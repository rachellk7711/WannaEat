# 영양 레이어 검토 — K-FIND 식품영양성분 DB

**상태: 보류.** 데이터 아키텍처는 사용자 검토 대상이므로 확정하지 않는다.
여기에는 측정 결과와 판단 근거만 적는다.

작성 2026-09-16

---

## 1. 무엇인가

식약처 K-FIND 식품영양성분 데이터베이스. 가공식품 DB **316,734건**(2026-08-28).

**기반 제품 DB가 될 수 없다.** 166개 칸 중 원재료명이 없다.
우리 판정은 "원재료명 목록에 내 제한 성분이 있나"이므로 영양 수치만으로는 성립하지 않는다.

**대신 우리 DB에 붙는다.** `품목제조보고번호`가 우리 `prdlst_report_no` 와 같은 키다.

---

## 2. 왜 붙일 가치가 있나

원재료 표시 순서로는 함량을 알 수 없다. 표시기준상 **중량 2% 미만은 순서 예외**이기 때문이다.
그런데 영양성분표의 수치는 제조사가 신고한 값이다.

```
지금        설탕이 원재료 앞쪽에 표시됨
붙이면      설탕이 앞쪽에 표시됨 · 당류 22g / 100g
```

추정이 아니라 신고값이다. 이 차이가 크다.

K-FIND 쪽 고유 품목보고번호는 309,324개인데 우리와 겹치는 것은 190,698개다.

**보정 (2026-09-17)** — K-FIND 보고번호 칸에 `2009026203637/2009026203638` 처럼 번호가 `/` 로 묶인 행이 1,568개 있었다. 번호별로 풀면 결합이 **192,042개(11.4%, +1,344)** 로 늘어난다. 또 한 보고번호에 K-FIND 행이 여러 개인 경우가 5,529개 있다(용량·맛이 다른 제품). 하나를 고르지 않고 모두 남긴다. 결합표는 `data/prepared/kfind_by_report.csv`, 스크립트는 `scripts/17_join_kfind.py` 다.
우리 DB가 과거 신고분까지 포함하는 반면 K-FIND는 현재 유통 중심이기 때문으로 보인다.

건기식이 0건인 이유는 K-FIND 건강기능식품 DB(5,556건)를 아직 파싱하지 않아서다.

## 4. 그래서 무엇을 할 수 있나

할 수 있는 것

- 결합된 11.4% 제품에 **총당류·나트륨·포화지방** 수치를 함께 보여준다
- 당류를 제한하는 사용자에게 순서 대신 실제 g 값을 제시한다

할 수 없는 것

- **성분별 함량을 말할 수 없다.** "설탕 12g"은 불가능하고 "당류 22g"만 가능하다.
  당류에는 원재료에 본래 있는 당과 첨가한 당이 섞여 있다
- 나머지 88.7%에는 아무 수치도 붙지 않는다

---

## 5. 검토가 필요한 지점

1. 11.4%에만 붙는 값을 화면에 넣으면, **있는 제품과 없는 제품이 달라 보인다.**
   "정보 없음"을 어떻게 표시할지 정해야 한다
2. 총당류는 첨가당과 천연당을 구분하지 않는다. WHO 권고는 **유리당** 기준이라
   총당류를 그대로 대면 기준이 어긋난다
3. 적재 용량 — 추출본이 46MB다. Supabase Free 용량 계산에 포함해야 한다
4. 갱신 주기 — K-FIND는 2026-08-28판이고 우리 제품 DB와 갱신 시점이 다르다
