# WannaEat 계획서 검증 결과

> **2026-09-18 후속 결정:** 사용자 기준은 `피해요 / 알려만줘요` 2단계로 변경했다. 아래 본문의 3단계 설정·후순위 허용 관련 의견은 당시 검토 기록이며 현재 구현 기준으로 사용하지 않는다. 현행 규칙은 [`PRD.md`](PRD.md)를 따른다. 피해요는 표시 위치와 관계없이 발견 시 불일치에 포함하고, 알려만줘요는 발견 사실만 안내한다.

> 작성자: Codex (OpenAI) · 작성자 표기일: 2026-09-16. 본문의 검토일은 당시 검토 기준일이다.

검토일: 2026-09-11. 대상: 현재 수정 중인 `계획서.md`, 사전검증·법무·데이터 인벤토리·인수인계 문서, `scripts/01_schema.sql`, `scripts/02_prepare_csv.py`, 로컬 원본·변환 CSV.

## 결론

**서비스 취지와 큰 기술 방향은 맞다. 전면 재설계할 필요는 없지만, 현재 SQL·적재 코드·판정 규칙을 그대로 확정하고 진행하는 것은 권하지 않는다.**

유지할 것은 ‘사용자가 먼저 기준을 정하고, 원재료 표시를 읽어 그 기준과 대조한다’는 흐름이다. 보완할 것은 다음 네 가지다.

1. **표시 후순위와 실제 소량을 구분한다.** 사용자의 ‘후순위면 허용’ 선택은 유지하되, 함량 측정이나 안전 보장으로 표현하지 않는다.
2. **데이터 충돌과 사용자 기준의 상태를 설계에 반영한다.** 실제 CSV에 현재 기본키로 적재할 수 없는 바코드 중복이 있고, 변환 과정에서 서로 다른 원재료 정보를 버린다.
3. **법적 의무·외부 서비스 약관·선택적 보호 장치를 분리한다.** 강제 크롭 같은 화면 규칙은 과도하게 확정했고, 외부 AI 보관·연령 제한·호스팅 상업 이용 조건은 덜 반영했다.
4. **핵심 이용 흐름을 먼저 시험하고, 무료 베타에서 반복 사용·지불의사·원가를 함께 확인한다.** 대규모 DB 최적화가 이 검증을 가로막으면 안 된다.

사용자가 새로 제안한 ‘유료 전환 예정일·가격을 미리 고지’하는 방안은 **추가 아이디어로 별도 보류**했다. 기존 계획에 없다는 이유로 결함 처리하지 않았으며, 결제 기능 개발도 이번 검토에서 요구하지 않는다.

## 1. 서비스 취지와 이용 흐름

### 잘 맞는 부분

`계획서.md` 32행 이후의 ‘기준 설정 → 제품 입력 → 원재료 확보 → 기준 대조’는 사용자 설명과 일치한다. AI는 원문을 읽고, 실제 대조는 정해진 규칙으로 수행하도록 분리한 것도 적절하다. 순탄수 계산·레시피 등을 MVP에서 제외한 판단도 유지한다.

### 보완할 부분

**① ‘먼저 기준을 정했다’는 상태가 필요하다.**

- 위치: `계획서.md` 37행, `scripts/01_schema.sql` 74~92행.
- 문제: 성분별 강도는 저장하지만, 설정 완료·선택한 모드·확정 시점이 없다. 행이 없는 상태가 ‘설정 전’, ‘기본값 사용’, ‘무관’ 중 무엇인지 정해져 있지 않다.
- 수정 방향: 최소한 설정 완료 상태와 기준 버전을 둔다. 추천값은 사용자가 확인해 확정하도록 하고, 이후 운영자가 추천값을 바꿔도 기존 사용자의 기준이 조용히 바뀌지 않게 한다. 화면뿐 아니라 분석 API도 설정 완료 여부를 검사한다. 사용자에게 모든 성분을 한 개씩 눌러 확정하도록 강요할 필요는 없다.

**② 결과는 함량 등급이 아니라 ‘표시 근거에 따른 내 기준 대조’여야 한다.**

- 위치: `계획서.md` 72~84행, 535~545행; `docs/02_법무-표현설계.md` 122~132행.
- 문제: ‘뒤쪽 → 소량 포함’, ‘없음 → 미포함’을 자동 연결한다. 성분이 세 개이고 비율이 40%·35%·25%여도 마지막 성분은 뒤쪽이다. 표시 순위만으로 실제 소량을 확정할 수 없다는 뜻이다. OCR에서 못 읽은 것과 실제 표시가 없는 것도 다르다.
- 수정 방향: **완전 제한 / 소량 허용 / 무관이라는 사용자의 선택은 유지**한다. 다만 ‘소량 허용’의 작동 방식은 ‘표시 후순위를 허용하는 개인 기준이며 실제 함량 측정은 아님’이라고 설정 시 설명한다. 결과는 ‘후순위 표시 — 설정한 기준 내’, ‘제한 성분 확인’, ‘읽은 표시에서 발견되지 않음’, ‘판단 보류’처럼 근거를 드러낸다. ‘완전 제한’도 앱이 완전 무함유를 보증한다는 뜻은 아니다.

**③ 부분 판독·복합원재료·재조회에 대한 흐름을 정한다.**

원재료 일부가 잘렸거나, 괄호 속 하위 원료와 전체 순서를 구분하지 못하거나, 사전에 없는 이름이 남으면 자동으로 ‘기준 내’라고 끝내지 않는다. 해당 부분 확인·재촬영·텍스트 수정으로 이어지게 한다. 반대로 중요하지 않은 미등록 단어 하나 때문에 모든 분석을 일괄 차단할 필요도 없다. ‘제한 성분 확인 여부’와 ‘판독 완전성’을 분리하면 된다.

과거 기록은 ‘당시 기준의 결과’로 보존하고, 현재 기준이 달라졌으면 재대조 버튼을 제공한다. 예전 결과를 그대로 현재 구매 판단에 쓰게 만들면 서비스의 핵심인 ‘내 기준’이 어긋난다.

## 2. 정확도와 근거: 통계로 확인한 것과 아직 모르는 것을 분리

**① 원재료 개수 일치는 정확도나 완전성을 증명하지 않는다.**

- 위치: `계획서.md` 881행, 913행, 1029행.
- 문제: 원재료명과 `RAWMTRL_ORDNO`의 개수 일치를 근거로 ‘실제 누락 1.4%’, ‘정렬하면 원래 표시 순서 복원’까지 확정한다. 둘 다 한 항목씩 빠져도 개수는 일치할 수 있고, 번호가 실제 포장 표시 순서와 같은지는 별도 문제다.
- 수정 방향: `ORDNO`는 **버리지 말고 보존**한다. 다만 실물 표시와 대조하기 전에는 ‘정렬 후보 키’로 다룬다. 일치율은 배열 정합성 지표로만 보고, 원료 누락률·OCR 정확도·실물 표시 순서 일치율과 구분한다. 계획서에 이미 있는 실물 20장 검증은 유효하지만, 첫 작동 점검이지 전체 시장 정확도의 증명은 아니다.

**② 실제 촬영한 라벨과 공공DB의 출처·시점을 섞지 않는다.**

공공DB는 후보 검색과 보조 정보에 유용하다. 그러나 같은 제품도 배합·포장 변경이나 잘못된 매칭이 있을 수 있다. 현재 구매 대상의 라벨을 충분히 읽었다면 그 표시를 대조의 주된 근거로 사용하고, DB와 충돌하면 출처·갱신일·차이를 보여준다. 흐린 라벨을 무조건 우선하라는 뜻은 아니다. 사용자 촬영 결과로 공공 마스터를 즉시 덮어쓰지도 않는다.

수입식품·건강기능식품처럼 DB 경로별 제공 필드가 다른 경우, 원재료 텍스트를 얻었다는 이유만으로 동일한 순위 판정까지 가능하다고 가정하지 않는다. DB에 없어도 라벨 판독 경로는 작동할 수 있어야 한다.

**③ 성분 카드의 ‘기관 기준 나열’도 편집 판단이다.**

- 위치: `계획서.md` 101행 이후의 카드 형식, 1397행의 조사 우선순위.
- 문제: 제조 시 사용기준, 일일섭취허용량, 허가 상태는 서로 다른 정보다. 국가별 숫자만 나란히 두면 같은 척도처럼 보일 수 있다. 원료와 첨가물을 나눈다는 이유만으로 원료의 조건·제한 확인이 항상 불필요해지는 것도 아니다.
- 수정 방향: 카드에는 최소한 대상 물질, 기준의 종류·단위·적용 조건, 출처·확인일을 갖춘다. 짧은 본문과 접힌 상세 설명은 유지한다. 모든 성분의 논쟁을 정리하는 거대한 자료집을 출시 선행조건으로 삼을 필요는 없다. 이번 검토는 예시 카드 전부의 과학적 사실을 인증한 것은 아니다.

### 먼저 통과시킬 작은 시험

실제 라벨로 정답을 직접 만든 뒤 다음 경우를 확인한다: 완전 제한 성분의 앞/뒤 위치, 후순위 허용, 별칭, 복합원재료, 일부 잘림, 미등록 성분, DB와 라벨 충돌, 기준 변경 후 재조회. OCR 문자 정확도뿐 아니라 **제한 성분을 놓쳐 ‘기준 내’라고 한 건수**, 판단 보류 비율, 결과까지 걸린 시간·수정 횟수를 함께 기록한다. AI가 스스로 출력한 신뢰도 숫자만으로 통과시키지 않는다.

## 3. 무료 베타가 수익화 가능성을 확인하는가

방향은 맞다. 다만 `계획서.md` 1488~1495행의 ‘본인 2주 사용’, ‘20명 중 10명 실사용’만으로는 유용성과 지불의사를 구분하기 어렵다. 본인 사용은 초기 점검에 유용하지만 본인과 다른 사용자의 행동까지 대표하지는 않는다.

베타에서는 아래 **세 질문**이면 충분하다.

| 확인할 것 | 최소 측정 방법 | 해석 시 주의 |
|---|---|---|
| 실제 구매에 도움이 되었나 | 분석 후 ‘선택에 도움 됨 / 안 됨’과 이유 한 가지 | 단순 접속·사진 업로드는 구매 도움과 다름 |
| 다음 구매 때 다시 쓰나 | 예: 2~4주 관찰 중 서로 다른 구매일에 반복 분석한 사용자 비율 | 기간과 분모를 먼저 정하고, 장보기 기회가 없었던 사람은 구분 |
| 돈을 받을 가능성이 있나 | 충분히 써 본 사람에게 명시적인 가상 가격·제공량을 보여주고 이용 의향과 유료 출시 알림 신청 측정. 건당 비용도 집계 | 가격 테스트임을 밝히고 결제처럼 속이지 않음. 응답·신청은 실제 결제의 증명이 아님 |

관찰 기간과 계속/수정/중단 기준은 시작 전에 정한다. 20명은 방향을 찾는 작은 실험으로 쓰되, 통계적으로 시장성이 확정됐다고 표현하지 않는다. 원가에는 실패·재시도·고정비·관리 시간을 포함한다. 전체 분석 건수보다 ‘구매 판단에 도움이 된 분석’의 비용도 보는 것이 좋다.

미리 유료 전환일·가격을 공지하는 새 아이디어는 별도 의사결정이다. 지금은 예정일을 약속하지 않아도 가격 가설을 시험할 수 있다.

## 4. 스키마와 아키텍처

### 유지할 구조

단일 웹 앱 + Supabase + 서버를 통한 OCR 호출이면 현재 규모에 충분하다. 원재료 원문 보존, 제품명 검색 인덱스, 작은 성분·별칭 사전, 결정론적 대조 규칙은 적절하다. 원재료를 전부 거대한 제품-성분 연결 테이블로 분해하거나, 벡터DB·마이크로서비스를 추가할 근거는 없다. 건강기능식품 부가정보를 별도 테이블로 분리한 것도 무리가 없다.

### A. 실제 CSV와 충돌하는 기본키 — 적재 전에 수정

위치: `scripts/01_schema.sql` 47~53행, `scripts/02_prepare_csv.py` 92행 이후.

변환된 `data/prepared/barcode_map.csv` 전체를 읽어 확인한 결과:

| 항목 | 실측 |
|---|---:|
| 데이터 행 | 259,669 |
| 서로 다른 바코드 | 229,040 |
| 바코드당 첫 행 외 추가 행 | 30,629 |
| 두 행 이상인 바코드 종류 | 25,479 |
| 둘 이상의 서로 다른 품목보고번호에 연결된 바코드 종류 | 13,740 |

현재 `bar_cd PRIMARY KEY`로는 이 파일을 그대로 적재할 수 없다. 이는 DB에 실제 COPY를 실행한 결과가 아니라, **전체 파일의 키 중복과 SQL 제약을 대조해 확인한 확정적 충돌**이다.

예: 바코드 `8801725020197`은 품목보고번호 `1994048423910`, `199404842394`에 연결된다. 하나만 남긴다고 올바른 제품이 확정되는 것이 아니다.

수정 방향: 원본 적재 영역에서 중복·충돌을 보존하고, 정리된 바코드-제품 관계는 여러 후보를 허용한다. 관계 중복 제거와 ‘이 바코드는 이 제품이다’라는 최종 선택을 분리한다. 복합키만 추가해도 내용이 다른 동일 관계의 충돌까지 해결되지는 않으므로 정리 규칙이 필요하다. 사용자에게는 후보가 불확실하면 제품명·제조사·라벨 확인으로 이어지게 한다.

### B. 중복 제거가 원재료 정보를 잃는다 — 적재 전에 수정

위치: `scripts/02_prepare_csv.py` 45~54행.

현재는 같은 품목보고번호가 다시 나오면 내용과 변경일을 보지 않고 버린다. 원본 C002·C006·C003에 스크립트와 같은 필수값 필터 및 처리 순서를 적용해 재확인했다.

| 원본 | 행 수 | 채택 | 필수값 부족으로 제외 | 중복으로 제외 | 중복 중 제품명·원재료·순서가 첫 채택 행과 다른 행 |
|---|---:|---:|---:|---:|---:|
| C002 | 1,073,137 | 1,073,004 | 132 | 1 | 1 |
| C006 | 569,470 | 567,598 | 1,005 | 867 | 100 |
| C003 | 46,042 | 46,041 | 1 | 0 | 0 |
| 합계 | 1,688,649 | 1,686,643 | 1,138 | 868 | 101 |

이번 데이터에서 채택 대상의 **서로 다른 서비스 간 번호 충돌은 발견되지 않았다.** 확인된 중복은 C002 또는 C006 내부에 있다. 따라서 서비스 접두사를 기본키에 붙이는 변경을 이번 실측만으로 필수라고 주장하지 않는다.

구체적으로 C002의 `1997040105594`에는 변경일이 모두 `20260703`인 서로 다른 제품명·원재료 행이 있다. 한 행에는 ‘볶은메밀가루’가 있고 다른 행에는 없다. 현재 스크립트는 메밀 원료가 있는 뒤의 행을 버린다. 원천이 잘못됐는지, 어떤 행이 유효한지는 별도 확인이 필요하며, **최신 변경일 하나만 택하는 방식으로도 이 사례는 해결되지 않는다.**

수정 방향: 완전히 같은 중복은 합치되, 내용이 다른 동일 번호는 충돌로 분리한다. 검증 전에는 어느 행도 확정적인 구매 판정 근거로 쓰지 않는다. 필수값 누락·중복·충돌의 건수와 제외 이유를 남긴다. 날짜의 달력 유효성, 출력 파일 완성 후 교체, 실패 시 이전 데이터 유지도 적재 절차에 넣는다. 이번 검토에서 날짜 오류를 발견했다는 뜻은 아니다.

### C. 서비스 흐름에 필요한 최소 보완

| 현재 위치 | 부족한 점 | 최소 보완 방향 |
|---|---|---|

| `product_alias` | 개인의 확인이 전역 정답으로 승격될 위험 | 개인 확인과 검증된 공용 매핑 구분. 동일 쇼핑몰 제목에 다른 옵션/제품이 있는 경우 처리 |

`result_json`을 쓰는 것 자체는 문제가 아니다. 위 정보가 이미 들어간다고 합의되어 있다면 별도 컬럼이나 테이블을 무조건 늘릴 필요도 없다.

**RLS는 현재 SQL에 없다.** 계획서 1132행에는 필요하다고 써 있지만, `01_schema.sql`에는 활성화·정책·권한 설정이 없다. 실험용 SQL로는 보완 중일 수 있으나 사용자 데이터 투입 전에는 막아야 할 항목이다. 실제 노출 여부는 배포 환경의 권한에 달려 있어 현재 유출됐다고 판단한 것은 아니다. 사용자 본인 행만 읽고 쓰는 정책, 공용 마스터의 관리자 전용 변경, 서버의 세션 검증을 함께 마련하고 익명·계정 A·계정 B로 교차 접근을 시험한다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)

### D. 인프라·갱신은 단순하게, 단 실패 조건은 명확하게

- **전체 DB 용량 실측은 진행할 가치가 있다.** 다만 CSV/JSON 바이트 합계가 PostgreSQL 실제 용량은 아니다. 적재 충돌을 정리한 뒤 테이블·인덱스별로 측정한다. Free DB는 500MB 초과 시 읽기 전용으로 바뀔 수 있으므로, 사용자 설정·인증과 함께 운영하는 DB에서 무턱대고 한계까지 실험하지 않는다. [Supabase 용량 안내](https://supabase.com/docs/guides/platform/database-size)
- **원본 다운로드의 시간 제한과 전체 사전 적재의 필수 여부는 다른 문제다.** 제품명 검색에는 로컬 데이터가 유용하지만, 원재료 캡처 경로의 작동을 169만 건 전체 적재 성공에 종속시킬 이유는 없다. 전체 적재 실험은 유지하되 핵심 흐름 검증과 분리한다.
- **모바일 업로드 크기 제한을 추가한다.** Vercel Function의 요청/응답 제한은 4.5MB다. 크롭만으로 준수가 보장되지 않는다. 클라이언트 크기 조절·압축, 실제 전송 본문 크기, 긴 라벨 가독성을 함께 검증한다. Base64를 쓰면 원본 파일보다 커지는 점도 반영한다. 이 문제 때문에 이미지 영구 저장소를 반드시 추가할 필요는 없다. [Vercel Function 제한](https://vercel.com/docs/functions/limitations)
- 증분 갱신은 서비스별 수정일 필드, 겹치는 조회 구간, 성공 후 체크포인트, 재시도·동일 입력의 중복 반영 방지, 주기적 누락 점검이 필요하다. 오류 응답이나 한 번 조회되지 않은 것을 제품 삭제로 처리하지 않는다. UPSERT 때 적재시각도 갱신한다. `raw_loaded_at DEFAULT now()`만으로 기존 행의 시각이 갱신되지는 않는다.
- `LCNS_NO`는 업소명과 같은 식별자가 아니다. MVP 검색에 당장 안 써도 원천에서는 보존한다. 생산종료도 판매 재고 소멸과 같지 않으므로 ‘제외해도 사용자 손실 없음’이라는 축소 근거는 수정한다.

## 5. 법무: 과한 부분은 줄이고 실제 요건을 보완

### 5-1. 화면 규칙을 법적 필수로 단정한 부분

위치: `계획서.md` 439~459행, 667~676행; `docs/02_법무-표현설계.md` 293~299행, 330~337행, 381행.

**‘크롭 건너뛰기 금지’, ‘빨강·초록 금지’, ‘국외이전 거부자에게 반드시 텍스트 입력 제공’은 이 서비스에 일률적으로 적용되는 법 조문 자체와 구분해야 한다.**

크롭·전송 전 확인·개인정보 제외 안내는 유지할 만한 좋은 보호 장치다. 다만 이미 원재료만 담긴 이미지라면 전체 영역 확인으로 끝낼 수 있고, 핵심은 원본 자동 업로드를 막고 필요한 픽셀만 보내는 것이다. 크롭했다고 주소·이름이 반드시 사라지는 것도 아니다. 거부 시 대체 입력도 유용하지만, 특정 대체 기능 구현을 법률상 절대 의무로 단정하려면 별도 근거가 필요하다.

식품표시광고법은 거짓·과장, 기만, 비방, 근거 없는 부당 비교 등을 제한한다. 특정 색만 사용했다고 곧바로 위법이 되는 규정으로 읽을 수는 없다. 반대로 ‘내 기준’이라는 문구나 중립 색이 실제로 잘못된 함량·안전성 주장을 면책하지도 않는다. 앱의 정보가 법상 표시·광고에 해당하는지와 표현의 전체 맥락을 보아야 한다. **권할 원칙은 ‘색상 금지’가 아니라 ‘근거가 있는 개인 기준 대조이며 제품 안전 등급이 아님을 명확히 하는 것’이다.** [식품 등의 표시·광고에 관한 법률, 제2·8·9조](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=269957)

### 5-2. 외부 AI 전송·보관 설명은 실제 계약에 맞춰 수정

- Gemini 무료 서비스는 입력·출력을 개선에 사용할 수 있고 사람의 검토도 가능하며, 개인정보·민감정보 등을 제출하지 말라고 명시한다. **사용자의 동의만으로 이 약관상 제한이 없어지는 것은 아니다.**
- 유료 서비스는 학습 사용을 배제하지만, 남용 방지 등의 제한적 로그 보관·임시 캐시까지 없어지는 것은 아니다. ‘우리 서버에 사진을 영구 저장하지 않음’과 ‘모든 업체가 즉시 삭제함’을 구분해야 한다.

[개인정보 보호법 제28조의8, 2026-09-11 시행본](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1029334869)

## 6. 업무 순서와 현실성

위치: `계획서.md` 1437~1527행.

스파이크, 즉 본개발 전에 작은 코드와 실제 데이터로 불확실성을 시험하는 접근은 좋다. 다만 현재는 DB 구조·전체 적재를 먼저 확정하고 핵심 이미지 입력이 6주차에 나온다. 사용자 취지에서 가장 먼저 실패 여부를 알아야 할 것은 **모바일 구매 상황에서 기준 설정과 판독 결과가 유용하게 연결되는가**다.

권장 순서는 다음과 같다. 전체 DB 실측을 없애자는 제안이 아니라, 무엇을 다른 작업의 선행조건으로 둘지 바꾸자는 제안이다.

1. **작은 제품 규칙 확정:** 설정 완료, 후순위 허용의 의미, 판단 보류, 출처 우선순위를 한 장으로 정한다. 대표 성분과 실제 라벨만 선정한다.
2. **핵심 흐름을 끝까지 시험:** 기준 설정 → 휴대폰 이미지 선택/촬영 → 필요한 영역 확인 → 원재료 추출 → 기준 대조. 판독·사용성·대략적인 원가를 함께 측정한다. 저장이 필요한 최소 스키마만 사용한다.
3. **데이터 구조·적재 실험:** 확인된 중복/충돌을 정리한 뒤 전체 적재 용량·제품명 검색을 측정한다. 사용자 기준·이력·RLS를 완성한다. 이 결과로 검색용 데이터 범위와 플랜을 결정한다.
4. **배포 전 점검 후 무료 베타:** 실제 전송/보관 안내, 공급자 조건, 계정 간 격리, 삭제, 요청 크기·비용 상한을 점검한다. 본인 사용 후 소규모 외부 베타에서 세 질문을 확인한다.

기존 G1의 ‘500MB 경로 확보’는 DB 전략의 통과 조건으로, G2의 제품명 검색은 검색 경로의 통과 조건으로 좁힌다. 실패했다고 핵심 촬영 서비스 전체를 중단할 필요는 없다. G3은 ‘실용 수준’ 대신 위 2절의 오판·보류·시간 지표를 사용한다. G5에는 관찰 기간·반복 사용·가격 반응을 추가한다.

**시간 합계 170시간은 산술상 맞고, 11~13주 버퍼를 인정한 점도 적절하다.** 다만 계획에 적힌 3a~3e는 74시간이 아니라 표 기준 90시간이다. 더 중요한 것은 ‘이력·즐겨찾기는 거의 공짜’, ‘무료 베타 인프라 고정비 0원’을 확정하지 않는 것이다. 기준 변경·삭제·권한 테스트와 적합한 유료 인프라 비용을 반영해 남은 작업을 다시 추정한다. 신규 대규모 콘텐츠 조사보다 핵심 흐름 실측을 앞세운다.

## 수정 중 흔적으로 분류한 것과 검토 한계

옛 API-only 설명과 새 CSV 다운로드 설명의 병존, 경쟁 앱 조사 전의 중단 기준, 이미 끝난 인증키 발급 작업은 **진행 상태 정리 항목**으로 분류했다. 이런 흔적을 근거로 계획 전체가 잘못됐다고 판단하지 않았다.

다만 `PRMS_DT`가 2017년 이전이라는 사실만으로 ‘2017년 이후 제공 안내는 웹 UI에만 적용’한다고 단정할 수는 없다. 최초 보고는 오래됐어도 변경·공개 시점이 나중일 수 있다. 이 해석과 인벤토리의 전수성·각 필드 설명은 공급기관 기준과 대조할 때까지 확정 근거로 삼지 않는다. 앞선 조사 문서의 결론을 그대로 승인한 검토가 아니다.

이번에 수행한 것은 문서·SQL·변환 코드 검토, 로컬 CSV의 읽기 전용 전수 집계와 충돌 사례 확인, 관련 공식 법령·공급자 문서 확인이다. 원본 계획서·코드·데이터는 변경하지 않았다. 실제 Supabase 적재·성능 측정, 휴대폰 OCR 시험, 사용자 인터뷰·결제 실험, 경쟁 앱 전수 실사용은 수행하지 않았다. 따라서 용량·인식률·수익화 성공을 실증 완료로 표시하지 않는다.

**다음 작업의 우선순위는 ‘판정 규칙과 데이터 충돌 처리에 대한 사용자 확인 → 초안 수정 → 작은 핵심 흐름 시험’이다.** 검토 결과만으로 새로운 스키마를 임의 확정하거나 외부 배포를 진행하지 않는다.
