## 배경 (이것만 알면 된다)

한국 **가공식품의 원재료명**을 조회해 사용자가 설정한 식단 기준(저탄고지 등)과 대조하는 웹 서비스를 만든다. 스택은 **Supabase(PostgreSQL) + Vercel**.

지금 필요한 것은 **"어떤 공공데이터가 존재하는지"의 완전한 목록**이다. 이 목록으로 데이터베이스를 설계할 예정이므로 **누락이 곧 설계 실패**다. 나중에 스키마를 다시 짜는 일이 없도록 **빠뜨리지 말고 전수 조사**해달라.

**⚠️ 스키마나 아키텍처는 설계하지 말아달라.** 조사 결과만 정리하면 된다. 설계는 발주 측에서 한다.

## 과제 1 — 전수 탐색 (가장 중요)

**위 목록에 없는 식품 관련 데이터셋을 모두 찾아라.** 특히 이런 종류:
- 제품별 원재료·성분 정보
- 영양성분 정보
- 첨가물 정보 (**용도·사용기준·사용량 제한**)
- **알레르기 유발물질** 정보
- 바코드 ↔ 제품 연계
- 제품 회수·부적합 정보
- 축산물·수산물 관련
- HACCP·인증 정보 (유기농·무항생제 등)
- 식품 표시사항 관련

## 과제 2 — 데이터셋마다 아래를 표로

| 항목 | 비고 |
|---|---|
| 데이터셋명 / 서비스ID / 제공기관 | |
| **응답 필드 전체 목록** (영문 코드 + 한글 설명) | 빠뜨리지 말고 전부 |
| **총 건수** | |
| **조인 가능한 키** | 품목보고번호 · 바코드 · 인허가번호 · 업소명 등 |
| 갱신 주기 / 최종 수정일 | |
| 제공 형태 | REST API / **파일 다운로드** / 둘 다 |
| 일일 호출 한도 · 1회 최대 행수 | |
| 인증키 발급처 | 공공데이터포털 vs 식품안전나라 |
| **⚠️ 알려진 제약** | 예: 09~19시 서비스 제한, 2017년 이후 데이터만 |

## 과제 3 — 조인 관계 지도

어떤 데이터셋들이 **어떤 키로 연결되는지** 정리하라. 축은 `PRDLST_REPORT_NO`(품목보고번호), 바코드, `LCNS_NO`(인허가번호).

## 과제 4 — 용량 추정

각 데이터셋의 **레코드당 평균 바이트**를 샘플로 측정하고 총 용량을 추정하라. Supabase 무료 500MB / Pro 8GB 중 무엇을 쓸지 판단하는 데 쓴다.

## 과제 5 — 파일 일괄 다운로드 가능 여부 ★

API 없이 **전체 파일(CSV/XLSX)을 한 번에 받을 수 있는** 데이터셋을 표시하라.
**107만 건을 1,000건씩 API로 긁으면 며칠이 걸린다.** 파일 다운로드가 되는지가 초기 적재 방식을 결정한다.

## 검증 원칙 (중요)

- **문서에 적힌 필드 목록을 그대로 믿지 마라.** `sample` 인증키로 실제 호출해 **원본 JSON 응답을 붙여라**
- 실호출로 확인한 것과 문서만 본 것을 **구분해서 표시**하라
- **09~19시에는 서비스가 제한될 수 있다** (실측 확인된 제약). 응답이 `ERROR-503`이면 시간대 문제다
- 확인 못 한 것은 **"확인 불가"** 로 남겨라. **추측으로 채우지 마라**
- 모든 항목에 **URL**을 붙여라
