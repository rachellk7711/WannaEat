## 1. 아키텍처 ⏸ 검토 대기

```
[브라우저]  이미지 선택 → 클라이언트에서 크기 조절 → 전송 전 확인 화면
     │                         (원본은 브라우저를 떠나지 않음)
     ▼  확인한 영역만 전송
[Supabase Edge Function]  ── Gemini API 호출 (키는 서버에만 보관)
     │                         AI는 글자 읽기만. 판정하지 않음
     ▼
[판정 엔진]  성분 정규화 → 고정 규칙으로 내 기준과 대조
     │
     ▼
[Supabase Postgres]  제품 마스터 · 성분 사전 · 사용자 기준 · 분석 이력
```

| 구성 | 선택 | 근거 |
|---|---|---|
| 프런트엔드 | **Cloudflare Pages** (Next.js 정적 빌드) | 무료 요금제에서 상업 이용 허용, 배포 횟수·대역폭 제한 없음 |
| API | **Supabase Edge Functions** | 무료 월 50만 호출, 실행 150초·CPU 2초 → AI 응답 대기에 여유 |
| DB·인증 | **Supabase Postgres / Auth** | 리전은 **서울** |
| AI | **Gemini (유료 요금제)** | 무료 요금제는 입력을 모델 개선·사람 검토에 사용할 수 있어 사용자 이미지에 부적합 |

> Vercel Hobby는 비상업 용도로 제한되고, Netlify 신규 무료 요금제는 월 배포 20회 한도가 있어 제외했습니다.

## 3. 원재료 표시 순서

공공DB의 원재료 문자열은 표시 순서대로 저장돼 있지 않은 경우가 많습니다. 순서 컬럼(`RAWMTRL_ORDNO`)으로 정렬해 복원합니다.

- C002 80만 행 검증: 오름차순 38.8% · 내림차순 23.0% · 뒤섞임 38.1%
- 정렬 후 세 그룹 모두 같은 분포로 수렴 — 앞쪽형 원재료(정제수·밀가루·설탕) 평균 위치 0.31~0.36, 뒤쪽형(정제소금·향료) 0.55~0.58. C006(9.5만 행)도 동일
- **한계:** 전체 데이터의 분포로 확인한 것입니다. 제품 하나하나가 실제 라벨과 같은지는 **실물 라벨 20장 대조**(9. 검증 계획)로 확인합니다. 그 전까지 순서는 "정렬 후보"로 다룹니다.
- **C003(건강기능식품)에는 순서 컬럼이 없습니다.** 이 경로는 순서를 표시하지 않습니다.

## 4. 판정 파이프라인

| 단계 | 처리 | 담당 |
|---|---|---|
| 1 | 이미지 → 원재료 텍스트 추출 (**표시 순서 보존**, 원문 전사 포함) | Gemini |
| 1' | (라벨이 없을 때) 제품명 → 공공DB 조회 → 순서 정렬 | DB |
| 2 | 성분명 → 표준명 정규화 (동의어·표기 변형 흡수, 괄호 구조 파싱) | 앱 |
| 2' | 표기 → **기준 원재료** 대응 (`돼지등심`→돼지고기, `박력분`→밀). 규칙 초안: `24_기준원재료_식별규칙.md` ⏸ 검토 대기 | 앱 |
| 3 | 표준명 + 발견 여부 → 피해요/알려만줘요 2단계 기준과 대조 (표시 위치는 참고 정보) | **고정 규칙** |
| 4 | 판독 완전성 판정 — 확인 불가 항목 집계 | 앱 |
| 5 | 미등록 성분은 검토 대기열로 → 사람이 승인 후 사전에 추가 | 사람 |

**원칙 1 — AI에게 판정을 맡기지 않습니다.** AI가 판정하면 같은 제품이 호출마다 다르게 판정됩니다. AI는 글자 읽기만 담당하므로 제공자를 교체해도 결과 규칙은 변하지 않습니다.

**2단계 설정 처리 (2026-09-18 사용자 결정):** `피해요` 성분은 표시 위치와 관계없이 발견 시 기준 불일치에 포함합니다. `알려만줘요` 성분은 발견 사실만 안내하며 불일치 개수에 포함하지 않습니다. 미선택 원재료는 개인 기준 대조 대상에서 제외합니다. 기존 SQL 제약·시제품 상태·기준 스냅샷의 변경은 별도 구현 작업이며, 과거 기준을 새 기준으로 소급 해석하지 않습니다.

**원칙 2 — 판정과 판독 완전성을 분리합니다.** 다음 세 가지는 "확인 불가"로 집계해 결과와 함께 표시하며, 절대 "발견되지 않음"으로 합치지 않습니다.

1. 하위 원료가 표시되지 않은 복합원재료 (복합조미식품·혼합제제·기타가공품 등) — 표본의 34%
2. 성분 사전에 없는 미등록 성분
3. 판독하지 못한 영역

**괄호의 뜻이 경로마다 다릅니다.** 공공DB 의 괄호는 "어떤 것인지" 를 밝히는 한정어(`콩기름(대두유)`)이고, 실물 라벨의 괄호는 복합원재료의 하위 원료입니다. 두 경로의 파싱 규칙을 나눠야 합니다.

## 5. 데이터 모델 (개요) ⏸ 검토 대기

| 테이블 | 역할 |
|---|---|
| `products` | 제품 마스터 — 제품명·업소·품목유형·원재료 원문·표시순서·출처 |
| `ingredient_master` / `ingredient_alias` | 성분 사전과 동의어 매핑 (앱 시작 시 메모리 적재) |
| `diet_modes` / `mode_default_rules` | 모드와 기본 판정값 |
| `user_criteria` / `user_criteria_state` | 사용자별 성분 설정(피해요/알려만줘요 2단계) + **설정 상태**(미설정 / 모드 기본값 / 직접 선택)와 기준 버전 |
| `analysis_history` / `criteria_snapshot` | 분석 이력 — 판정일·제품명·판정 결과·확인 불가 수와 **당시 기준 스냅샷**을 함께 보존 |
| `ingredient_feedback` | 미등록 성분 검토 대기열 |

**성분 사전 진행 상황 (2026-09-17):** 공공 마스터 대조로 **제품 완전 판독 96.72%** (기반 사전만일 때 81.8%). 검증 과정에서 정규화 오류 두 건(끝 숫자 삭제로 비타민 B1·B2·B6·B12 가 한 토큰으로 합쳐짐, 이명 칸을 괄호 안에서도 나눔)을 고쳤습니다. 남은 미매칭 24,124종은 LLM 분류 단계에서 처리합니다. 목표는 **99.9%**입니다 (`04_성분사전_구축계획.md`).

- 원재료명은 **문자열 그대로 보관**하고 파싱은 앱에서 합니다. 성분 단위로 쪼갠 조인 테이블은 행이 500만~1000만 개로 늘어나면서 얻는 것이 없습니다(성분→제품 역방향 검색은 1차 버전에 불필요).
- 제품명 검색은 정규화 함수 + 트라이그램 인덱스로 처리합니다.
- 상세 DDL은 별도 문서로 제출하며, 적재 전에 검토를 거칩니다.

## 7. 보안·개인정보

- 사용자 데이터는 **행 수준 보안(RLS)** 으로 본인 것만 읽고 쓰게 합니다. **1차 구현에 포함**하며, 익명·타 계정으로 교차 접근을 시험해 실제로 막히는지 확인합니다. 공용 데이터(제품·성분 사전)는 로그인 사용자에게 읽기만 허용하고 쓰기는 서버만 합니다.
- DB 리전은 **서울**입니다. 다만 AI 처리는 국외에서 이뤄지므로 국외 이전 사실을 고지합니다.
- API 키는 저장소에 넣지 않고 서버 환경변수로만 관리합니다.
- Gemini 약관에 따라 서비스 대상은 **18세 이상**입니다.
- 상세 문안은 `02_법무-표현설계.md`를 따릅니다.
