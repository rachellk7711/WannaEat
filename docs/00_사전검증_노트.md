### 중간 종합 — 계획에서 바뀌어야 할 것

**두 갈래 경로 모두 "깨끗하지 않다"는 것이 확인됐다.**

| 경로 | 난관 |
|---|---|
| 온라인 (장바구니·상세페이지 캡처) → 제품명 매칭 | **매칭 난도 상.** 자동확정 30~50% 추정, 사용자 확인 단계 필수 |
| 오프라인 (실물 라벨 촬영) → OCR | **인식률 중.** 환각·누락 위험, 크롭·신뢰도 게이트 필수 |
| 수입식품 | **공공DB에 아예 없음.** 저탄고지는 수입품 비중이 높음 |

> **결론: "캡처 한 장 → 자동 판정" 이라는 매끄러운 그림은 성립하지 않는다.**
> 다중 경로 + 폴백 + 사용자 확인을 전제로 UX를 설계해야 한다.
> 이것을 **약점이 아니라 정직함**으로 포지셔닝하는 것이 오히려 신뢰를 만든다 —
> 원재료·건강 정보에서 "모르는 걸 모른다고 하는 것"은 경쟁 우위가 될 수 있다.

**공통 원칙 (V1·V2가 독립적으로 같은 결론에 도달):**
1. **크롭 강제** — 정확도(V1) + 개인정보(법무) 두 이유가 수렴
2. **신뢰도 게이트** — 임계 미달 시 판정하지 않고 사용자에게 확인받는다
3. **정밀도 우선** — 오류 비용이 비대칭이다. 못 찾는 것보다 잘못 찾는 것이 훨씬 나쁘다
4. **사용자 확인 결과를 자산으로 축적** — alias 캐시 · 성분 사전 모두 같은 성장 루프

## V4 — 공공DB 원재료명 조회 (1차 확인 결과)

### 결론: **통과.** 제품명으로 원재료명을 조회할 수 있다.

**API: 식품안전나라 오픈API `C002` — 식품(첨가물)품목제조보고(원재료)**
- 공공데이터포털: `data.go.kr/data/15062098`
- 형식: JSON / XML, **무료**
- 활용신청 수: 3,630건 (2026-09 기준)
- **호출 제한: 1회 요청당 1,000건**

### 요청 파라미터

| 파라미터 | 필수 | 설명 |
|---|---|---|
| `keyId` | 필수 | 인증키 |
| `serviceId` | 필수 | 서비스명 (`C002`) |
| `dataType` | 필수 | `xml` / `json` |
| `startIdx` / `endIdx` | 필수 | 요청 범위 (페이징) |
| `PRDLST_NM` | 선택 | **품목명 검색** |
| `BSSH_NM` | 선택 | **업소명(제조사) 검색** |
| `RAWMTRL_NM` | 선택 | **원재료명 검색** (역방향 조회 가능) |
| `PRDLST_REPORT_NO` | 선택 | 품목제조번호 |
| `PRDLST_DCNM` | 선택 | 품목유형명 |
| `LCNS_NO` | 선택 | 인허가번호 |
| `PRMS_DT` | 선택 | 보고일자 |
| `CHNG_DT` | 선택 | 변경일자 (YYYYMMDD) |

### 응답 필드

| 필드 | 설명 | 우리 용도 |
|---|---|---|
| `PRDLST_NM` | 품목명 | **제품 매칭 키** |
| `BSSH_NM` | 업소명 | **제조사 매칭 보조** |
| `RAWMTRL_NM` | **원재료명** | **핵심 데이터** |
| `RAWMTRL_ORDNO` | 원재료 표시순서 | 함량 순서 추정 |
| `PRDLST_DCNM` | 품목유형명 | 부분 적재 시 필터 기준 |
| `PRDLST_REPORT_NO` | 품목제조번호 | 고유 식별자 |
| `LCNS_NO` | 인허가번호 | 제조사 식별 |
| `PRMS_DT` | 보고일자 | 데이터 시점 |
| `CHNG_DT` | 변경일자 | 증분 갱신 기준 |
| `ETQTY_XPORT_PRDLST_YN` | 내수/겸용 구분 | 국내 유통 여부 |

**유통기한 필드는 없다.** (우리에겐 불필요)

### 원재료명 형태 — 파싱하기 쉽다

쉼표로 구분된 **단일 문자열**로 제공된다.

```
"설탕,D-소르비톨,식염2,인산염,냉동연육,전분"
```

- 콤마로 split하면 바로 성분 목록이 된다
- 샘플에 **설탕·전분**이 포함 → 저탄고지 판정 대상 성분이 실제로 잡힌다
- ⚠️ `식염2` 처럼 **숫자 접미가 붙는 표기**가 존재 → 정규화 필수

### ⚠️ 발견된 구멍 — 수입식품

**수입식품 제품DB (`data.go.kr/data/15073949`) 에는 원재료명이 없다.**

| 제공 필드 | 신고제품구분코드/명, 제조국가코드/명, 제품명(`PRDT_NM`), 육류품목코드/명, 품목코드/명, 수입식품등 관리번호 |
|---|---|
| **원재료명** | **없음** |
| 제조사 | 없음 (제조 국가만) |
| 데이터 규모 | 약 92,564건 |

**영향:** 저탄고지 실천자가 자주 사는 **수입 제품**(MCT오일, 수입 무설탕 초콜릿, 수입 견과류·프로틴바 등)은 공공DB로 원재료명을 얻을 수 없다.
→ **라벨 촬영 폴백 경로가 반드시 필요하다.** V1이 중요해지는 이유.
→ 다른 API에 대안이 있는지는 교차검증 중.

### 미확인 사항 — 인증키 발급 후 즉시 측정

**데이터 총 건수는 공개 문서에 없다.** 웹 검색으로 확인 실패. 다만 **API 응답에 `total_count`가 포함되므로 인증키를 받아 1회 호출하면 즉시 확정된다.**

**개발 1주차 첫 작업 — 이 호출 하나로 적재 전략이 결정된다:**

```
https://openapi.foodsafetykorea.go.kr/api/{인증키}/C002/json/1/1
```

`total_count` 값에 따른 분기:

| 총 건수 | 추정 용량 (레코드당 ~400B) | 전략 |
|---|---|---|
| ~50만 건 이하 | ~200MB | **전량 적재 가능** |
| 50만 ~ 100만 | 200~400MB | 전량 적재 가능하나 인덱스 포함 시 빠듯 → 컬럼 선별 |
| 100만 건 초과 | 400MB+ | **부분 적재 필수** — `PRDLST_DCNM`(품목유형)으로 필터 |

※ 인덱스(GIN trigram/bigram)가 원본 대비 상당한 용량을 차지하므로 **여유를 크게 잡아야 한다.**

**추가 확인 필요:**
- 인증키 발급 소요 시간, 일일 호출 한도
- ⚠️ **`openapi.foodsafetykorea.go.kr` 샘플 키는 09~19시 서비스 제한** (V2에서 실측 확인) → 실제 발급 키도 동일 제한이 있는지 확인. 있다면 **야간 배치로 덤프**해야 한다
- 2001~2023년 데이터를 연도별·품목별로 제공한다는 안내가 있으나 API의 실제 커버 범위는 호출로 확인

## V1 — Gemini 라벨 OCR

### 판정: **중** — 조건부 가능. 단 검증 장치 없는 자동화는 불가

크롭 + 고해상도 설정 + 구조화 출력 + 사전 기반 검증을 갖추면 양호한 라벨에서는 실용적일 가능성이 높다. 그러나 **한국어 소형 인쇄체에 대한 공개 벤치마크가 사실상 존재하지 않아** 실측 없이는 확신할 수 없다.

### 발견 1 — 이미지 토큰 상한이 물리적 병목이다

Gemini는 이미지를 **768×768 타일**로 쪼개 타일당 258토큰으로 처리한다. `media_resolution` 설정별 이미지 토큰 상한은 `low` 280 / `medium` 560 / `high` 1120 / `ultra_high` 2240(Gemini 3 전용)이다.

**즉 4000×3000 사진을 통째로 보내도 모델이 보는 유효 해상도는 제한된다.** 라벨 전체를 보내면 원재료명 영역이 차지하는 토큰은 전체의 일부에 불과하다.

> **→ 해상도를 올리는 것보다 "원재료명 영역만 크롭해서 관심 영역이 토큰 예산을 독점하게 만드는 것"이 훨씬 효과가 크다.**

**이 결론은 `02_법무-표현설계.md` §5-2의 개인정보 대응과 정확히 같은 방향을 가리킨다.** 크롭 강제는 개인정보 방어선이자 정확도 향상 수단이다. 두 이유가 수렴하므로 **크롭 UI는 타협 없이 필수**로 확정한다.

### 발견 2 — VLM은 못 읽을 때 조용히 지어낸다

NeurIPS 2025 KIE-HVQA 연구: 기존 MLLM은 **블러·가림·저대비** 하에서 시각적 열화를 충분히 지각하지 못하고 **언어적 사전지식에 과의존해 환각을 생성**한다.

한국어 실사용 실패 사례(Gemini 2.5 Pro)에서 확인된 유형:

| 실패 유형 | 실제 사례 |
|---|---|
| **중간 누락** | 표 항목 다수가 빠졌는데 **시작과 끝은 정확해서 즉시 발견되지 않음** |
| **환각** | "추가적 업무를" → "주인의식을 발휘하여 적극적으로 업무를" |
| **1글자 오인식으로 의미 반전** | "AI 평가 안함" → "AI**가** 평가 안함" |

식품 라벨에 이게 정확히 해당한다. `정제소금`, `산도조절제`, `혼합제제`, `밀(미국산)` 같은 표현은 **모델이 문맥만으로 그럴듯하게 만들어낼 수 있는 고빈도 도메인 어휘**다. 성분 판정 앱에서 최악의 실패 — 없는 성분 생성, 있는 성분 누락 — 가 조용히 발생할 수 있다.

또한 원재료명은 `A(B(C), D), E` 형태의 **중첩 괄호 구조**인데, Gemini Flash는 밀집 표에서 셀 내용이 밖으로 이동하는 **구조 붕괴**가 보고되어 있다.

> **→ 신뢰도 게이트가 필수다.** 성분 사전 매칭률, 판독 가능도(`legibility`) 자기보고, 2회 호출 diff를 조합해 임계 미달 시 **판정을 내리지 않고 원문을 보여주며 사용자 확인을 받는다.**

### 발견 3 — 한국 라벨은 법적으로 아주 작을 수 있다

「식품 등의 표시·광고에 관한 법률 시행규칙」 별표 3:
- 활자 **10포인트 이상**, 장평 90% 이상, 자간 −5% 이상
- **정보표시면 100㎠ 미만이면 장평 50%까지 축소 허용**
- **면적 부족으로 10pt 표시가 불가하면 해당 규정을 따르지 않을 수 있음**

장평 50%로 눌린 한글은 자형 판별 난도가 급증한다. **껌·스낵 소포장·소스 파우치 같은 소용량 제품이 최악 케이스**이며 실측 세트에 반드시 포함해야 한다.

### ⚠️ 발견 5 — pg_trgm의 한글 지원이 보장되지 않는다

PostgreSQL `pg_trgm`은 `KEEPONLYALNUM` 매크로 때문에 **빌드 옵션에 따라 한글 트라이그램이 생성되지 않을 수 있다.** pg_bigm 공식 문서는 pg_trgm의 비알파벳 언어 전문검색을 "Not supported"로 분류한다.

**Supabase에서 배포 전 반드시 실행할 검증 SQL:**

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
SELECT show_trgm('초코파이');                        -- 빈 배열이면 한글 미지원
SELECT similarity('초코파이', '오리온 초코파이 정');    -- 0이면 미지원
SELECT word_similarity('초코파이', '[무료배송] 오리온 초코파이 정 12개입 1박스');
```

`show_trgm`이 비면 → **애플리케이션단 bigram 인덱스 테이블로 대체**해야 한다 (관리형 DB는 pg_bigm 설치가 막혀 있는 경우가 많음).

> **이건 개발 1주차에 가장 먼저 확인할 항목이다.** 여기서 막히면 매칭 아키텍처 전체를 다시 짜야 한다.

### 발견 6 — 오류 비용이 비대칭이다 (설계 원칙)

```
못 찾음  →  "정보 없음"에 그침
잘못 찾음 →  엉뚱한 제품의 원재료를 보여줌 → 건강 오판
```

**따라서 재현율(recall)보다 정밀도(precision)를 우선한다.** "많이 맞히는" 쪽이 아니라 **"틀리지 않는"** 쪽으로 보수적으로 잡는다.

**3구간 임계값 + 마진 규칙**

| 구간 | 조건 | 동작 |
|---|---|---|
| 자동 확정 | score ≥ 0.90 **AND** 브랜드 일치 **AND** 식품유형 일치 **AND** (top1 − top2) ≥ 0.10 | 바로 표시 + 근거 배지 |
| **사용자 확인** | 0.55 ≤ score < 0.90 또는 동점 후보 존재 | **후보 3~5개 카드 제시** |
| 매칭 실패 | score < 0.55 또는 후보 0 | "원재료 확인 불가" + 라벨 촬영·바코드 유도 |

**마진 규칙이 임계값보다 중요하다.** `설탕대신 알룰로스`처럼 동일 품목명이 여러 업소에 존재하면 top1·top2가 사실상 동률이다. **점수가 높아도 마진이 없으면 절대 자동확정하지 않는다.**

**식품유형(`PRDLST_DCNM`) 하드 게이트:** `초콜릿` vs `초콜릿가공품` vs `준초콜릿` vs `캔디류`는 원재료 구성이 완전히 다르다. 카테고리가 다르면 점수와 무관하게 탈락시킨다.

### 발견 7 — alias 캐시가 가장 효과 큰 패턴

사용자가 후보를 고른 순간 `(정규화 상품명 → 품목보고번호)`를 저장하면, 이후 동일·유사 상품은 **정확 조회**로 전환된다.

**쇼핑몰 상품명은 롱테일이지만 인기 상품은 극단적으로 편중**되므로, 수백~수천 건만 쌓여도 자동확정률이 크게 오른다. 이것이 `04_성분DB·룰셋설계`의 "성장 루프"와 같은 구조다.

### 정규화 파이프라인 (개발 시 구현)

**파괴적 삭제가 아니라 필드 분해로 설계한다.** `92%`, `C8`, `500ml`는 후보 변별에 결정적이므로 지우면 안 된다.

