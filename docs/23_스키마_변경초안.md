# 스키마 변경 초안 — 검토용

**상태: 초안 · 보류.** 데이터 아키텍처는 사용자가 직접 검토하기로 한 영역이다.
`scripts/01_schema.sql` 은 **고치지 않았다.** 이 문서는 지금 설계가 무엇을 담지 못하는지와 바꿀 방향을 적는다.

작성 2026-09-17 · 근거 `docs/20`(Codex 검증) · `docs/21`(최종 검증) · `docs/24`(기준 원재료 식별)

---

## 1. 지금 설계가 담지 못하는 것

`01_schema.sql` 은 성분 사전을 `ingredient_master`(표준명 하나 + 분류)로, 사용자 기준을
`user_criteria(ingredient_id, strength)` 로 둔다. 검증 이후 확인된 사실과 맞지 않는 곳이 다섯 군데다.

| # | 사실 | 지금 설계의 문제 |
|---|---|---|
| 1 | 사용자가 고르는 것은 **기준 원재료**(설탕·밀·돼지고기)이고, 하나에 표기가 수백 개 걸린다(돼지고기 직접 469종) | 기준 = 성분 하나로 묶여 있다. `돼지등심`·`박력분` 을 기준에 잇는 자리가 없다 |
| 2 | 매칭에 **확신 두 단계**(직접·추정)와 **묶음 표기**가 있다 | 결과가 "있다/없다" 뿐이다. 「확인 필요」·「확인 불가」를 담을 칸이 없다 |
| 3 | 근거는 **주장 단위**로 검토 상태가 다르다(ADI 는 확인, EU 조건은 자동) | 성분 행 하나에 근거가 묶인다. 주장별 출처·검토 상태가 없다 |
| 4 | 같은 성분에 **기관마다 결론이 다르다**(MSG: EFSA 30 / JECFA 수치 불필요) | 한 성분에 한 값만 둘 수 있다 |
| 5 | 원본은 **버전이 있는 스냅샷**이다(K-FIND 2026-08-28판, FDA 2026-07-28 갱신) | 적재 시점만 있고 원본 버전·해시가 없다 |

## 2. 바꿀 방향

### 2-1. 기준 원재료 (1·2번)

```
criteria                기준 원재료 — 사용자가 고르는 단위
  id            text PK          'sugar', 'wheat', 'pork' …
  name          text             '설탕', '밀', '돼지고기'
  grp           text             곡물·전분 · 당류·감미료 · 콩·두류 · 동물성 원료 · 기름·견과·씨앗 · 첨가물·기타
  sort_order    int

criteria_rule           규칙 원본 (data/curated/criteria_rules.csv)
  criterion_id  text FK
  kind          text             정확 · 접두 · 접미 · 포함 · 제외 · 제외접미
  confidence    text             직접 · 추정
  pattern       text
  note          text

criteria_token          규칙을 토큰에 적용한 결과 (18 이 생성, 조회용)
  criterion_id  text FK
  token         text
  confidence    text             직접 · 추정
  rule          text             어떤 규칙이 걸렸나 (검수·설명용)
  ruleset_ver   text
  PK (criterion_id, token)

opaque_token            묶음 표기 (확인 불가)
  token         text PK
  rule          text
```

`user_criteria.ingredient_id` → `criterion_id` 로 바뀐다. `strength` 는 **`피해요` · `알려만 줘요`** 두 값이다
(2026-09-17 결정 — `완전 제한 / 소량 허용 / 무관` 을 대신한다. 원재료 표시에 사용량이 없어 소량은 판정할 수 없다).
**프리셋(모드 기본값)은 두지 않는다** — `mode_default_rules` 는 없앤다.

기준 목록·예시·검색어는 DB 조회 대신 **버전 붙은 JSON 을 앱에 넣는다**(`data/prepared/criteria_catalog.json`, 76KB).
사용자 기준 한 줄은 `{kind: 'criterion' | 'subgroup', id, strength}` 이고, 목록 전체에 `rulesetVersion` 을 붙인다.
`subgroup`(예: `seed_oils`)은 판정 때 그 시점 카탈로그로 펼친다(`docs/24` §2-1 결정 5).
로그인 연동 전에는 기기 Storage, 이후 `user_criteria(user_id, kind, target_id, strength)`.
이력(`analysis_history`)에는 **펼쳐진 기준 ID 목록**과 `rulesetVersion` 을 남긴다.

**판정 결과는 네 갈래**로 저장한다 — 발견 · 확인 필요 · 확인 불가 · 없음.
라벨 사진 경로에서는 규칙을 **실시간으로** 적용해야 하므로(토큰 목록에 없는 표기가 나온다)
`criteria_token` 은 캐시일 뿐이고 규칙 엔진이 원본이다.

### 2-2. 주장 단위 근거 (3·4번)

```
substance               근거를 붙이는 대상 (성분 카드 단위)
  id            text PK          'erythritol', 'caramel_class3' …
  name_ko       text

substance_alias         라벨 표기 → 대상
  alias         text PK          '카라멜색소ⅲ', '암모니아카라멜'
  substance_id  text FK
  scope         text             단일 · 묶음 이름   (소르비탄지방산에스테르 → 5종)

evidence_claim          주장 하나 = 행 하나
  id              bigserial PK
  substance_id    text FK
  claim_type      text   ADI · 평가결론 · 섭취권고 · 상한섭취량 · 승인상태
                         · 국내 사용상태 · 국내 사용조건 · EU 허용조건 · 역할
  institution     text   EFSA · JECFA · FDA · WHO · 보건복지부 · 식약처 · EU
  state           text   수치 있음 · 수치 불필요 · 우려 없음 · 자료 부족
                         · 안전성 인정 안 됨 · 평가 없음 · (국내) 사용가능 …
  value / unit    text
  basis           text   무엇 기준인가 (아질산 이온 · 유리 이미드 · 인 …)
  population      text   consumers · children …
  quote           text   원문 인용 — 요약하지 않는다
  eval_date       date
  source_link     text
  source_record   text   원 레코드 ID (ToxRef UUID, EU policy code …)
  source_snapshot bigint FK → source_snapshot
  review_status   text   자동 후보 · 검토 대기 · 승인 · 반려
  reviewed_at     timestamptz
```

**기관마다 따로 행을 둔다.** 숫자가 있다거나 최신이라는 이유로 하나를 고르지 않는다.
카드는 `review_status = 승인` 인 행만 모아 만든다.

### 2-3. 원본 스냅샷 (5번)

```
source_snapshot
  id           bigserial PK
  source       text      'I1020' · 'EFSA OpenFoodTox 3.0' · 'K-FIND 가공식품' · 'FDA Substances' …
  version      text      제공처가 밝힌 판/갱신일 (모르면 '미상')
  fetched_at   timestamptz
  sha256       text
  rows         bigint
```

`data/manifest/*.json` 이 지금 이 역할을 파일로 하고 있다.

### 2-4. 영양 레이어 (보류)

```
product_nutrient          K-FIND — 품목보고번호 하나에 여러 행이 붙을 수 있다 (5,529개)
  prdlst_report_no  text
  food_cd           text
  food_nm           text
  basis             text          100g · 1회 제공량 …
  kcal / carb_g / sugar_g / sodium_mg / sat_fat_g / trans_fat_g   numeric
  report_no_raw     text          '/' 로 묶인 원본 표기
  source_snapshot   bigint FK
  PK (prdlst_report_no, food_cd)
```

결합률이 11.4% 라 화면에서 "정보 없음" 을 어떻게 보일지 먼저 정해야 한다(`docs/19` §5).

## 3. 바꾸지 않는 것

- `products` — 그대로. 다만 괄호 안 한정어(`콩기름(대두유)`)를 판정에 쓰므로 원문 칸을 반드시 보존한다
- 사용자 테이블(`user_criteria_state` · `criteria_snapshot` · `analysis_history`) — 참조 대상만 `criterion_id` 로 바뀐다
- RLS 원칙 — 공용 마스터는 읽기 전용, 쓰기는 서버만
